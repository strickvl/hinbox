# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with
code in this repository. Any design docs that you write can be stored in the
`design/` folder (which is ignored by git).

## Running commands

We use a `justfile` as the single task runner. Run `just` to see all available
commands, or `just <command>` to execute one. All recipes use `uv run` to
guarantee the lockfile venv is used (matching CI).

## Common Commands

### Development
- **Format code**: `just format` (ruff fix + format via `uv run`)
- **Lint code**: `just lint` (ruff check + format verification)
- **Run CI checks locally**: `just ci` (lint, file-length check, tests — the same recipes GitHub Actions calls)
- **File length limit**: `just check-file-length` fails if any tracked `.py` file is over 1000 lines. It runs in `just ci` and in GitHub Actions. Split the file rather than raising the limit.
- **Install dependencies**: `uv sync`

### Main Application
- **Process articles**: `just process` (CLI interface to main functionality)
- **Check database**: `just check` (view article statistics)
- **Start web interface**: `just frontend` (the reader on http://localhost:5001; listens on 127.0.0.1 only unless `HINBOX_FRONTEND_HOST` says otherwise); `just demo-reader` opens it on a made-up corpus (`scripts/demo_reader_data.py`, written to `data/demo/`), which the README screenshots use; `just export-site <out>` writes it as a static site (`src/frontend/export.py`: renders each page through the app, follows links, rewrites them to relative files, in-browser search from `static/search-index.js`, no filters; the side panel is built in the browser from the source's exported page and the verdicts each entity page carries as JSON (`cite_data()` in `views.py`), and falls back to the source page when opened from disk)
- **Reset processing**: `just reset` (reset article processing status)
- **Domain management**: `just domains` / `just init <name>`
- **Evaluate a model**: `just eval <relevance|merge> --model <model>` scores it against the hand-labelled gold sets in `{output_dir}/eval/`; `just eval show` prints the scoreboard (`--grid`: latest score per model × prompt file); `--prompt-variant <name>` scores `<prompt>.<name>.md` whatever the model; `just eval placement --model <model>` scores which starter heading profile sentences are filed under against hand labels (`src/evals/placement.py`); `just eval subplacement --model <model> --labels <file>` scores which sub-heading of their section new sentences are filed under (`src/evals/subplacement.py`); `just eval-mine` picks hard merge pairs to label; `just eval-replay --model <model>` grows long profiles by replaying well-covered entities' articles in date order (snapshots for the profile-update eval); `just eval-cases --model <model>` turns those snapshots into profile-update test cases; `just eval profile-update --model <model> --split dev` runs the pipeline's profile update on those cases and scores it without a model (collapse, kept facts, unchanged text, added sentences, citing the article, invented citations, keeping both sides of a disputed year; a new-fact case with a claim label in `eval/claim_labels.jsonl` must also state each core fact in a sentence backed by the article (its own citation or the next one in its paragraph) and add no listed wrong reading or invented "sources disagree" sentence, see `src/evals/claim_labels.py`; only `reviewed` labels count unless `--claim-labels draft`; `--rescore <run file>` scores a saved run again without model calls); it scores the edit-list updater (`src/engine/profile_edits.py`) that the pipeline uses; add `--approach rewrite` to score the old whole-profile rewrite instead, or `--approach facts` for the fact-list prototype (`src/engine/fact_list.py`: the model never sees the whole profile; it extracts quoted claims from the article, code finds the few existing sentences on the same thing, the model calls each claim same/new/conflict, a repeat is only counted on its row unless it comes from a new kind of source, a conflict is written by code right after the old sentence, and new facts are placed one section at a time; prompts `fact_extract.md`, `fact_compare.md`, `fact_write.md`)
- **DSPy experiments**: `just dspy-merge --model <model> --optimizer <none|bootstrap|mipro|gepa>` optimises the merge check and scores it on the same scoreboard; `just dspy-profile --model <model> --reflection-model <model>` runs GEPA on the edit-list profile updater and scores it with the profile-update eval; `just dspy-test` runs its offline tests

### Testing
- Run `just test` to execute the suite under `tests/`.
- Pass extra pytest args: `just test -k test_merger --tb=short`
- CI runs lint + tests on every PR via `.github/workflows/test.yml`.
- Key coverage areas include embedding similarity, lexical blocking, name-variant candidates, misfiled-location and misfiled-organization filtering, ALL CAPS recasing, spelling variants, per-type threshold resolution, embedding fingerprints, entity mergers, merge dispute agent routing, extraction caching/retry, canonical name selection, name variant detection, profile grounding, profile versioning, privacy mode enforcement, LLM multi-tool-call recovery, tracing (span nesting across threads, Instructor calls, `--local` endpoint guard), the web reader (`tests/test_frontend.py`: claims split as grounding splits them, verdict marks, pages on made-up tables), and corrections (`tests/test_corrections.py`: the file, contradictions, drawing them, the reader's forms; `tests/test_corrections_pass.py`: strikes cut and replaced, restatements, the edit guard, the run report, the reader after a run).
- Async tests (`@pytest.mark.asyncio`) are excluded in CI due to a missing pytest-asyncio configuration.

## Architecture Overview

### Entity Processing Pipeline
The CLI entry point `src/process_and_extract.py` coordinates the pipeline end to end using a parallel producer/consumer model:

1. **Configuration Loading**: `DomainConfig` reads `configs/<domain>/` to resolve Parquet input paths and output directories.
2. **Article Loading**: PyArrow loads the domain's article table and normalises rows before processing.
3. **Relevance Checking**: `ArticleProcessor.check_relevance` calls the helpers in `src/engine/relevance.py` (Gemini or Ollama) to skip irrelevant sources. Only runs with `--relevance-check`. It asks with the same labelled-section layout as the merge check (`src/utils/sectioned_prompt.py`): the domain's `relevance.md` minus its JSON "Output Format" section becomes the instructions, the article goes in its own section, and the model writes reasoning before `is_relevant`; an unreadable reply falls back to the structured prompt. If the check itself fails (API error, bad response), the article is skipped with reason `relevance_error`, kept separate from a real `not_relevant` verdict, and retried on the next run. A `not_relevant` verdict is stored in the processing-status sidecar with the article's content hash and a fingerprint of the model, prompt layout (`RELEVANCE_PROMPT_LAYOUT`) and relevance prompt (`ArticleProcessor.relevance_fingerprint()`); later runs reuse it without an LLM call while all three are unchanged (respects `cache.articles.skip_if_unchanged`; `--force-reprocess` re-checks). A letters-to-the-editor page (3+ letters each signed on its own line, "Ray Turner, Kendall"; `split_letters()` in `src/utils/letters_page.py`) is checked one letter at a time (`ArticleProcessor.check_letters_relevance()`), and only the relevant letters are extracted and kept as the article text for stubs and profiles, so signers and names from off-topic letters don't become entities; the kept and dropped signers and the kept letters' positions (`kept_letters`) go in the relevance outcome's `meta`, and later runs rebuild the same text from them (`stored_letters_text()`), so a stub from the page is later written in full from the kept letters only.
4. **Parallel Extraction**: Multiple extraction workers process articles concurrently via `ThreadPoolExecutor`. At most `performance.queue.max_buffered_articles` articles (never fewer than `extract_workers`) are submitted but not yet merged (`ordered_window()` in `src/utils/article_window.py`); the next is submitted each time the merge thread moves on, so extraction can't run far ahead and take the local model's slots from merge calls. Within each article, the 4 entity-type extractions also run in parallel. A shared LLM semaphore (`configure_llm_concurrency()`) bounds cloud API concurrency.
5. **Extraction Caching**: `ExtractionSidecarCache` (`src/utils/extraction_cache.py`) stores extraction outputs as JSON files keyed on content hash, model, entity type, prompt hash, schema hash, and temperature. Version-based invalidation lets you bump the cache version in config to force re-extraction without deleting files.
6. **Misfiled locations**: after the four extractions, `drop_misfiled_locations()` (`src/utils/misfiled_locations.py`) drops "locations" that are really people or organizations: a name that came back as a person in the same article (multi-word, or typed "other"), a name with an institution word ("Department", "Agency", "Sheriff"…), or an organization name from the same article or the organizations equivalence groups typed "other" (CIA, ACLU, ISIS, Senate). It also drops nationality words ("Yemeni"), news outlets ("Miami Herald"), laws ("NDAA") and dates ("March 2008"), whatever their type (`non_place_reason()` in `src/utils/non_place_names.py`). Dropped names go in `phase_outcomes["misfiled_locations"]`. The locations prompt also lists what isn't a location. `drop_misfiled_organizations()` drops an organization whose name is a person from the same article, titles and initials ignored ("President Donald Trump"), a country that came back as a `country` location from the same article ("France" typed "government" when an article lists countries), or a camp or base typed military/government/other ("Camp 7", "Guantanamo Bay Navy Base", "Guantánamo detention center"); dropped names go in `phase_outcomes["misfiled_organizations"]`. Before both, `recase_entity_names()` (`src/utils/name_case.py`) puts an ALL CAPS name copied from a dateline into the case the article uses elsewhere, or title-cases it for locations (`phase_outcomes["recased_names"]`).
7. **Quality Controls & Retry**: `src/utils/quality_controls.py` validates extraction output (required fields, name normalisation, within-article dedup) and profile quality (min length, citation regex, tag count, confidence range). Failures are captured in `PhaseOutcome` objects (`src/utils/outcomes.py`). When severe QC flags (`zero_entities`, `high_drop_rate`, `many_duplicates`, `many_low_quality_names`) are detected, the extractor automatically retries once with a repair hint. Profile QC runs inside `create_profile()` / `update_profile()` before each version is saved. First `repair_profile_citations()` (`src/utils/citation_ids.py`) snaps a cited article ID that isn't one of the profile's `sources` but is a few characters from exactly one of them back to that source (local Qwen sometimes drops or repeats a chunk of the ID), in the text and in saved fact rows, and adds the `citation_ids_repaired` flag. QC then applies safe fixes (default tags, clamped confidence) and records `{"passed", "flags"}` under `profile["qc"]`. A failing profile is kept and logged, never regenerated.
8. **Entity Merging**: `EntityMerger` follows an evidence-first cost structure — cheap checks run before expensive LLM calls:
   - **Lexical blocking**: RapidFuzz pre-filters candidates using configurable thresholds from the `dedup` section of domain config.
   - **Batched embeddings**: `embed_batch_result_sync()` computes vectors for all new entities at once rather than one-by-one.
   - **Similarity scoring**: Per-entity-type similarity thresholds and embedding fingerprints (`"{model}:{dim}"`) ensure model-change detection.
   - **Match checking**: LLM-based match verification only runs for candidates that pass the cheap filters. The prompt gives each input its own labelled `[[ ## field ## ]]` section (type rules included) and asks for written reasoning, then `is_match` and `confidence` under their own headers, as plain text via `text_generation()` (built with `src/utils/sectioned_prompt.py`; `parse_sectioned_reply()` reads it; an unparseable reply falls back to the structured `MatchCheckResult` prompt). On the hard merge eval set this layout plus reasoning cut false merges of related events; either one alone did not.
   - **Name-variant fallback**: when no candidate clears the similarity threshold, a candidate with a spelling variant of the incoming name still goes to the match check (`names_are_variants()` in `src/utils/name_variants.py`, searched over every entity, not just the capped lexical shortlist). Variants: the same name after `normalize_for_match()` (which drops accents, so "Guantánamo Bay" = "Guantanamo Bay"), a configured equivalence group ("Gitmo"), for locations/organizations the same core name without a leading "the"/"U.S.", a trailing "County"/"City" or a trailing "in/at/near …" description, one word respelled as a plural, ordinal or shortened form ("Commission"/"Commissions", "11"/"11th", "Counterterror"/"Counterterrorism"), or middle words dropped with the same first and last word ("Guantánamo Navy base" / "Guantánamo Bay Navy Base"); for organizations also "X administration"/"X government" with two spellings of one person ("Bush administration" / "George W. Bush administration"); for people the same first and last name ("Donald J. Trump"), the same last name with a first name shortened or one letter off ("Clay"/"Clayton", "Shelley"/"Shelly"), or the reverse, a bare surname ("Trump"), or a two-word-or-longer end of the full name ("Hadi al Iraqi" / "Abd al Hadi al Iraqi"); for events the same words in any order ("Firing of Harvey Rishikof as convening authority") or one run of up to two words added ("CIA waterboarding of …" / "Waterboarding of …"; words added in two places don't count). Common transliterations count as one spelling for people and events (Sheik/Shaikh/Sheikh, Mohammed/Muhammad, Qaida/Qaeda). A lone first or middle name ("Lara" / "Lara Tur", `lone_name_in_full_name()`) goes to the match check only when exactly one person in the table fits, so a bare "John" with ten Johns goes nowhere. Substring containment and derived acronyms don't count. On the merge gold set this sends 22 of 25 labelled-same pairs to the match check (was 12) and 1 of 166 labelled-different pairs (unchanged). If the match check rejects the closest candidate, the next-closest above the threshold is checked, up to `HINBOX_MERGE_MAX_SIMILAR_CHECKS` (default 3) candidates (`next_candidate()` in `src/engine/merge_candidates.py`), then the best name-variant candidate gets one more match check. From the second candidate on, the evidence carries `rejected_note()`: a closer candidate was already judged different, related entities from the same story are different, answer yes only for the same one. On the 7 Nov 150-article run about 6 merges were lost because a sibling event from the same story outranked the real one and only one candidate was checked. When a person is named by surname alone ("Rubio") and the candidate is the only person in the table with that surname, the match check's evidence says so (`surname_note()` in `src/engine/merge_candidates.py`), and the people rules tell it to match unless the context points to someone else; on the 7 Nov run Luna rejected "Rubio"/"Marco Rubio" without it.
   - **Merge dispute agent**: When a match result falls in the "gray band" (similarity within ±`MERGE_GRAY_BAND_DELTA` of threshold) with confidence below `MERGE_UNCERTAIN_CONFIDENCE_CUTOFF`, `MergeDisputeAgent` provides a second-stage LLM analysis that can override the initial merge/skip decision. Deferred cases are appended to `{output_dir}/merge_review_queue.jsonl` for human review. When the final verdict is skip or defer, the incoming entity is created as a new entity rather than dropped (unless an entity with the same key already exists, which is never overwritten).
   - **One spelling per kind**: an entity's `type`/`event_type` reached the merger as an Enum (fresh extraction), as `"LocationType.MILITARY_BASE"` (extraction cache, whose JSON wrote enums with `str()`) or as `"military_base"` (saved table), and organizations and locations are keyed by (name, type), so the same place missed its exact match and the same-key guard; the 12 Nov full run saved 51 locations and 60 organizations twice ("United States" 504 and 400 sources, "Pentagon", "Obama administration"). `plain_kind()`/`plain_kinds()` (`src/utils/entity_keys.py`) give the configured string; the merger applies it to each extracted entity, `load_existing_entities()` to each saved row (when two saved rows would then share a key, the second is kept exactly as saved, under its saved spelling or a numbered key, so it still saves and shows in the reader as its own page, and a warning counts them), the cache writes `model_dump(mode="json")`, and `sanitize_for_parquet()` saves an Enum as its value. Pairs already saved twice are joined by `scripts/join_kind_twins.py --run <copy of the entities folder> [--local] [--dry-run] [--hubs-only]` (`src/engine/kind_twins.py`): the row with the most sources is kept, each article only the other row has is fed to it oldest first with the pipeline's own `update_or_fill()` (a country, region or outlet is only linked), the other row is dropped, and the tables are saved after each pair; an article whose update fails is left out and the next is tried (not asked twice: at temperature 0 Qwen gave the same runaway reply in two passes), both rows stay, and the kept row holds the articles that went in, so the next run asks only for the rest (in the 12 Nov run's copy 110 of 112 pairs joined; one article each of "U.S. Department of Defense" and "Joint Task Force" sent Qwen's edit reply past its length limit, in the JTF case reasoning inside `article_says`). Then run the pipeline on that folder with `--limit 0` so the changed profiles' citations are checked and no article is read.
   - **Canonical name selection**: 5-layer deterministic scoring (`score_canonical_name()` in `src/utils/name_variants.py`) picks the best display name, penalizing acronyms, generic phrases, contextual suffixes, and ALL CAPS names (`is_shouting_name()`; a same-name-in-normal-case incoming entity replaces an ALL CAPS one).
9. **Profile Versioning**: `src/engine/profiles.py` maintains `VersionedProfile` history whenever entity content changes. A new entity gets a stub profile, not a model call (`src/engine/profile_stubs.py`): the article's sentences that name it, up to 3 (for people also sentences with only the surname, unless the article names someone else with that surname, "Keith Parrella" beside Jennifer; an alias made only of words from the name, "Miami" for "Miami Shores", is not searched for; an event's extracted description first; for locations and organizations a sentence that uses the name only as a label, "the USS Cole case", "Pentagon officials", comes last, and a stub made only of such sentences ends with an uncited note saying so, `only_as_label()`/`label_note()`), each cited, with `profile["stub"] = True` and no version history. When a second article merges in, `update_or_fill()` first writes the real profile from the stub's article (`create_profile()` on its text, looked up in `article_texts`, which `main()` fills from the loaded articles), then updates it with the new article, so a two-article profile costs the same two calls as before; if the first article's text is missing the stub itself is updated. A failed update keeps the stub and leaves the article unlinked. `HINBOX_PROFILE_STUBS=off` writes a full profile for every new entity again. Hub kinds listed under `profiles.link_only` in the domain config (default: locations typed `country` or `region`, and organizations typed `media`, whose profiles in the 7 Nov pilot were mostly the stories they ran: McClatchy 11,428 characters from 31 articles, and about 6 of 40 sampled sentences said anything about the outlet itself) are frozen after the first article (`src/engine/hub_profiles.py`): `update_or_fill()` makes no model call and changes no text, it only adds the article to `sources` and `profile["linked_only"]` (which `scripts/audit_entities.py` doesn't count as uncited); `HINBOX_HUB_LINK_ONLY=off` updates them like any entity. For people (`HINBOX_SECTION_REORGANISE`: default `people` for cloud and local models alike, `DEFAULT_LOCAL_TABLES`; local runs were flat until the 9 Nov 150-article Qwen rerun put 59 of 100 sure hand-checked sentences under the right heading and 93 of 100 under the right top-level heading, against 24 of 59 on 8 Nov and Luna's 64 of 69; most misses are the wrong sub-heading under the right top-level one; `on` for every table, `off`, or a comma list of tables such as `people,organizations`; `tables_enabled()` in `src/engine/section_split.py`), a profile that passes `HINBOX_SECTION_REORGANISE_CHARS` (default 8000) after an update is first given its kind's starter headings, once per entity (`src/engine/section_reorganise.py`; lists under `profiles.starter_headings` in the domain config, by entity table then `type` or `default`; `update_profile(..., kind=)` gets the entity's `type` or `event_type` from `update_or_fill()`; people store the extracted `type` since this change, so older people tables have none and the bench takes `--kinds`): its paragraphs (`_units()`, text before the first heading kept on top when it ends at a citation and is at most `OPENING_CHARS` (1500), old heading lines dropped) are numbered, one call is shown each starter heading with what it is for (`- Background: origin, life and activities before capture` in the config, `starter_notes()`) and puts each paragraph under one or up to 2 new headings (a new heading sharing a word with another heading refuses the answer), code moves them word for word, starter headings in list order, and undoes it if a sentence changes; the numbered pieces are each paragraph's (or line's: model-written profiles put one newline between paragraphs) cited sentences, shown grouped by paragraph, so a sentence about the capture inside a paragraph about someone's origins can go under the capture heading (pieces of one paragraph that stay together are joined again; `HINBOX_REORGANISE_PIECES=paragraphs` numbers whole paragraphs as before, `unit_spans()`; in a replay KSM's capture and waterboarding sentences sat in three mixed paragraphs and no "Capture and CIA custody" section was made), and the prompt says court items (rulings, motions, lawyers' arguments, testimony) go under the legal heading even when about custody or health, and a statement heading only holds the person's own words; `profile["reorganised"]` (`done`/`refused`) stops a second try, except that a refused one is asked again once the profile has grown 25% past `profile["reorganise_refused_chars"]` (a local replay refused al Nashiri's once, "1 sections", and one sub-section of the flat profile reached 14,114 characters), and a failed call is tried again next update; `scripts/section_split_bench.py --reorganise` tries it. The pieces are filed by the placement-only prompt (`src/engine/section_place.py`, 8 pieces per call: for each piece a few words on what it tells about the entity, then one starter heading), which on 204 hand-labelled sentences (`just eval placement --model <m> [--labels <file>]`, `src/evals/placement.py`, labels in `{eval_dir}/placement_labels.jsonl`, approaches `reorganise` and `classify`, accuracy and balanced accuracy over `sure` rows) was right on 93.6% for local Qwen and Luna, against 84-87% for the one-call reorganise prompt that may add headings (`HINBOX_REORGANISE_ASSIGN=sections` brings it back). After each later update of a reorganised profile, `place_new()` asks the same prompt about the cited pieces the update added and moves one filed under another top-level heading, word for word, to the end of that heading's own text (a piece answered with the first starter heading, Background, stays, since in local replays Qwen moved Guantánamo news there; so does one opening with a word that leans on the sentence before, "However", "As of", "That"; a heading left empty is dropped; undone if any sentence or citation claim changes; `HINBOX_SECTION_PLACE=off`). Then `place_new_subs()` (`src/engine/section_subplace.py`) asks, for each new cited piece in a top-level section with 2+ sub-headings, which of that section's sub-headings it belongs under, by name alone, or "None of these" (the top of the section), with the split's refiling prompt (`sub_messages()`), and moves it word for word to the end of that sub-section's own text, right after its last citation (a piece leaning on the sentence before stays; each move undone if a sentence or citation claim changes; `HINBOX_SUB_PLACE`: `on` by default, `local`, `off`). In the 9 Nov local run 31 of 55 misplaced new sentences came from the edit's anchor (the parent heading or a nearby sentence, not the sub-heading) and 11 from `place_new()`, which never files into a sub-heading; on 91 sure hand labels from that run (`just eval subplacement --model <m> --labels <file>`, `src/evals/subplacement.py`; gold a sub-heading, `(above)` or `(none fits)`, the last two right when the answer is "None of these"; never pushed) the run had 46 right and this step would leave 63/73 right for Qwen and 70/66 for Luna (2 seeds); showing each sub-heading with its first sentence did worse on both, since that sentence was often misfiled itself. With `HINBOX_SECTION_SPLIT` (same values and defaults), `update_profile()` then splits each top-level section (no higher heading above it, so a sub-section the split made is never split deeper) whose own text passes `HINBOX_SECTION_SPLIT_CHARS` (default 6000) with 6+ numbered pieces (`src/engine/section_split.py`): a split refused once is stored in `profile["split_refused_json"]` and asked again only when its section has grown 25% (`RETRY_GROWTH`; a local replay asked one refused split at 9 updates in a row); a reply that leaves every paragraph under one heading is first asked again once, shown its own answer and why it can't be used (`reask()`, `ONE_GROUP`), since in a 9 Nov local run Qwen gave Trump's "Campaign statements and policy" one heading at 6,900, 9,200 and 11,800 characters and the section reached 14,440; resumed from that state, the re-ask split off one paragraph, the renamed section split properly at the next update, and the longest section ended at 5,348 characters (7,202 and growing without it); one call on the update's model assigns piece numbers to 2-6 sub-headings one level down (a heading that is long, not plain text, or already in the profile, even with its words reordered or a year added ("Judge Authority and Appeals (2018)" beside "Appeals and Judge Authority"), refuses the split; a repeat keeps its first place, a missing piece joins its neighbour), code moves the pieces word for word, sub-sections in the order of their first piece, and undoes the split if the sorted sentences differ. The split call also says in a few words what each sub-heading covers; its headings are then kept and its pieces filed again by the placement-only prompt with those notes (`refile_split()` in `src/engine/section_place.py`, 8 per call; for a top-level section a piece answered "None of these" stays above the sub-headings; a piece with no usable answer keeps the split's choice; fewer than 2 sub-headings left, a failed call, or a refiling that would change any citation's claim text (a piece kept above the sub-headings ahead of piece 1 would take the uncited text above the section), keeps the split's plan; `HINBOX_SPLIT_REFILE`: `local` by default, `on`, `off`), since in 3 local replays of Spath, Trump and Obama 30 of Qwen's 40 wrong placements in a hand check (Luna 18 of 20) were the right top-level heading but the wrong sub-heading; with it Qwen's right placements went from 44 to 59 of 90 (3 alternated runs each), Luna's from 87 to 78 of 120 (4 each), hence local only. `covers` and the placement answer's `starts_with` (its sentence's first three words, copied) are required in the schema the model sees (Qwen left a defaulted `covers` out for 89 of 107 sub-headings), and an answer whose copied words aren't its sentence's is dropped (`read_reply(..., sentences)`), since some answers' notes described another sentence of the batch. On a profile marked `reorganised: done`, a sub-section one level under a top-level heading that passes the same size is re-split into 2-6 headings at its own level that replace it (one may keep its name; paragraphs put under another sibling's name, in other words too, join the end of that sibling's text, beside at least one new heading, and are not refiled, undone if any citation's claim text changes; the prompt doesn't offer this, since told it could, local Qwen named only siblings (in a Luna replay Spath's "Al-Nashiri Proceedings (2014–2015)" reached 10,349 characters because each re-split named a group after its sibling "Relocation Order Challenge (2015)" and was refused); at most `MAX_SIBLINGS` (8) under one parent; `long_sections(resplit=True)`), so the outline stays one level under the starter headings: in a 40-article replay al Nashiri's "#### Legal Mail and Prison Conditions" had reached 8,542 characters. For the same profiles the edit call is shown the starter headings with their notes and asked to anchor each new fact in its section, or its sub-section (`src/engine/section_routing.py`, `edit_profile(kind=)`, which `update_profile()` and the eval pass); an `add` anchored on a starter heading the profile lacks (with or without `#`, copied with its note, or with the note's "(not in the profile yet)" mark) creates it before the next starter heading the profile has, else before any heading the reorganise added (`insert_missing_heading()`; `edit_report["new_headings"]`, `edit_report["routed"]`). `scripts/section_placements.py <eval>/profile_replay/<model> --out <dir>` lists where each sentence an update added after the reorganise landed (review file for hand marking, counts per section, headings updates created, longest section, depth). For a reorganised profile an `add` anchored on a parent heading goes at the end of the parent's own text, before its first sub-heading (`_section_end(own=True)`), not into its last sub-section; an anchor that is a heading's words without `#` anchors on that heading (it was glued onto the heading line); an `add` whose text opens with a heading the profile has goes into that section (its sub-headings shifted to the profile's levels), and other heading text in an add is dropped in a reorganised profile (`edit_report["dropped_headings"]`; a local Qwen replay opened an END add with "## Release or transfer" over a trial-venue fact and 56 trial sentences followed it there) or kept no higher than the top level in a flat one; `HINBOX_SECTION_ROUTING=off` drops the note and this placement. The routing note also says the text above the first heading only says who the entity is. If a reorganised profile's opening (that text) still passes `HINBOX_OPENING_SORT_CHARS` (default 2000) after an update, one call is shown its numbered cited sentences, the profile's top-level headings and the missing starter headings, with notes, and "Opening"; code moves each piece word for word to the end of its section's own text (right after its last citation, so an uncited sentence there keeps its claim), or under a starter heading it creates, and keeps piece 1, an unplaced piece and one under an unknown heading in the opening. It undoes the move if a sentence changes or any citation's claim text would change, and asks again only once the opening has grown 25% past `profile["opening_sorted_chars"]` (`src/engine/opening_sort.py`; `HINBOX_OPENING_SORT=off`). In a 40-article local replay, KSM's opening grew from 562 to 11,336 characters, because new facts were anchored on its sentences and the split never looks above the first heading. Why people only: over 8 Luna dev runs with routing against 4 flat runs (7 Nov), reorganised person profiles passed 87/96 against 42/48 flat, organizations 87/112 against 45/56, events 75/96 against 43/48; in 40-article replays of KSM, al Nashiri and Pohl no sentence was lost by the reorganise or split, and the longest sub-section stayed under 7,100 characters (al Nashiri's had reached 8,540 before the re-split). A piece is a paragraph or list item, a long one cut into sentence runs, and always ends at a citation; text after a section's last citation is not numbered and stays at its end, so every cited claim keeps its exact text and grounding verdict. A profile with saved fact rows (`fact_rows_json`) is not split. `scripts/section_split_bench.py sections|cases` tries it on a finished run (review file of placements, claims the next grounding pass would re-judge) or writes split copies of the profile-update eval cases (`--eval-dir` then scores them). Storing one copied sentence per article for hubs was tried and dropped: over 1,620 articles only about 5 of 30 sampled sentences said anything about the country itself. `just eval merge --existing-profile stub` scores the merge check against stubs instead of saved profiles. Creation drafts once, fixes citations and tags in code (a first profile has one source), and makes one more call only for missing headings (refused if any word changes) or an empty draft (`src/engine/profile_create.py`). `HINBOX_PROFILE_CREATE_APPROACH=reflect` (or `create_profile(..., approach="reflect")`) brings back the old draft plus up to 3 reflect/regenerate rounds (`iterative_improve()`; the reviewer never sees the article, so it only judges format); `just eval profile-create --model <m> [--grounding]` compares the two on the same entity/article pairs. Updates apply a list of edits from one model call (`src/engine/profile_edits.py`, no reflection). A local model writes that reply under length limits (`src/engine/edit_limits.py`, `LimitedEditList`: `maxLength`/`maxItems` in the JSON schema sent to the server, which llama.cpp turns into the grammar it samples from, so a string that reaches its limit can only be closed; no limit is over 2,000, which llama.cpp refuses): in the 12 Nov full run 255 of 24,942 edit replies ran to the 16,384-token limit inside one string (a citation ID repeated without end in a copied profile sentence, or the model arguing with itself in `article_says`), the update failed, and at temperature 0 every retry wrote the same reply. A value exactly as long as its limit was cut: `without_cut_off()` drops an edit whose anchor was cut, trims a cut text to its last complete citation (drops it when a piece is there twice or none is complete), and only counts cut `disagreements`/`new_facts` (`edit_report["cut_off"]`, `hinbox.fields_cut` on the span). The limits are in the schema only, not Pydantic constraints, so a server that ignores them never has a long complete reply refused; `HINBOX_EDIT_REPLY_LIMITS=off` sends the plain schema. A reply no limit bites is the same with and without them (6 of 6 replayed on Qwen, byte for byte). `scripts/edit_limits_bench.py <run>/traces/run-*.jsonl --out <dir> [--runaway N --long N --limits on|off]` replays a run's runaway and long edit prompts with the limits (a recorded reply does not come back at temperature 0 days later even with the plain schema, so only replays where a limit bites say anything about the limits). Before they are applied, `guard_edits()` (`src/engine/edit_guards.py`) drops each new sentence that restates an existing one (every word of it, filler like "the article states" aside, in one old sentence and in the same order, with no year, month, number or name that sentence lacks, the same number of negations and the same hedges like "could" or "expected", and not framed there as someone's claim or denial) or says sources disagree when no old sentence sharing a topic word gives a different year, or a different month or count in the same year (a source's own date, "the 2009 article", ignored). A dispute that names the old value after "rather than", or whose anchor gives another count or year (`_anchor_differs()`), is not dropped as invented even when no topic word links it to that sentence ("death toll" against "killed"); it goes to the model check. A "sources disagree" sentence about something that changes over time (hunger-strike counts, a trial date, who holds a post, a status; not a one-off event such as a capture or plea) whose disputed sentence (the edit's anchor, else the old sentences with another value) cites only articles from other days is rewritten as the article's own side, dated ("As of April 2013, 59 captives were hunger strikers.^[id]", or "A June 2018 report identifies Pohl as the judge.^[id]"), by `later_update()` and `src/engine/later_updates.py`; this needs `article_dates` (published date by article id), which `merge_entities()` passes to `update_profile()` from the entity's linked articles (`article_dates()`) and the eval looks up in the domain's articles Parquet (`case_dates()`). `edit_report["guard"]` lists what was dropped and rewritten (`later_updates`); `dispute_check`). Every "sources disagree" sentence still left, and every softer comparison with an old sentence to set it against ("The article reports … 2,974 people, rather than 2,976", "A later report gives … instead"; `_SOFT_DISPUTE`, never dropped as invented, since "rather than" can be news), then goes to one model call per update (`src/engine/dispute_check.py`, prompt in code, the update's own model) with the sentence(s) it disputes (`_disputed_olds()`: the anchor paragraph's sentences giving another value) and both sources' dates; the model answers `conflict` (kept), `later` (replaced by the article's fact, dated), `different` (replaced by the plain fact) or `same` (dropped); a replacement that still compares sources or repeats a profile sentence is dropped, and a failed call keeps the sentence. On the 14 such sentences of the 7 Nov 150-article Luna run only 2 were real; `HINBOX_DISPUTE_CHECK=off` turns the check off. A new sentence about the profile itself ("The article states there are 104 captives, conflicting with the profile's count of 93"; `is_profile_note()` in `src/engine/profile_notes.py`: any mention of "the profile" it is being added to; "The profile also acknowledged …", about a review board's file on a captive, is not one, `_DOCUMENT`) is handled as a "sources disagree" sentence, whose guards it used to skip: a later state is dated (`later_update()`), the dispute check decides the rest and a real conflict stays with "the profile" reworded as "another report" (`reworded()`), and without that call (or when it fails) the article's half is kept alone (`plain_side()`: "There are 104 captives.", dated "As of March 2016, …" when it says how things stand; a half that is not a sentence keeps a source in front, "A March 2016 report notes 41 captives at the camp"), unless the note says outright that sources disagree (and gives the profile a side: "while the profile does not specify a cost, the article states …" disputes nothing) or its half leans on the other half ("it was reduced to 149", "he suspended the sentence", "this amount"), in which case it stays, reworded. A note that is an invented dispute (no old sentence gives another value) keeps the article's half when that is a sentence of its own, since it may be news. The article's half is what is left when the clause naming the profile is cut ("…, a date not specified in the profile", a bracket, `_without_profile()` in `later_updates.py`), "the article's report that B", or what the profile is said to state when an article is cited; a half with a second verb whose subject was the article keeps a source ("A report states that A, and identifies B"), and a citation copied from the profile's sentence ("…^[old].^[new]") is not put on it. A note with no fact from the article ("The article does not mention his age, whereas the profile …", "(no conflict …)", "This contradicts the profile's claim …", the model thinking aloud: "Wait, …", a question, "The profile has 116 and 122.") is dropped, and the same note twice in one reply is rewritten once (`edit_report["guard"]["profile_notes"]`: sentence, `plain`/`reworded`/`repeat`/`empty`/`conflict`, new text). In the 12 Nov full run Qwen wrote such a sentence 3,881 times in 24,687 edit replies and 1,701 were in the saved profiles, two thirds of them marked partly or not supported by the citation check. `scripts/profile_notes_bench.py <run>/traces/run-*.jsonl --out <dir> --articles <parquet> [--ask N --model <m>]` runs the guards over a run's recorded edit replies without a model (beside what they did before this guard) and, with `--ask`, with the dispute check's model call. A profile over `HINBOX_PROFILE_VIEW_CHARS` (default 16000) is shown to the edit model shortened by `profile_view()` (`src/engine/profile_view.py`): the text before the first heading (up to a quarter of the budget), the headings (up to a third), then the passages (paragraphs, list items, or sentence runs of a long paragraph) sharing the most words, names and years with the article, rarer words counting more, in their original order with `[… N passages not shown …]` markers and a note saying the profile was cut; the edits are applied to the full stored text, so nothing is cut from storage and the guards still check the whole profile (`edit_report["profile_chars_shown"]`). The match check and dispute agent cut an existing profile the same way around the new evidence at `HINBOX_MATCH_PROFILE_CHARS` (default 8000), and a profile's embedding is taken from `embedding_text()` (its opening, headings and first passages up to `HINBOX_PROFILE_VIEW_CHARS`); `0` turns either budget off. A profile still too long for the local model's window (`PromptTooLongError`) is updated by the fact-list updater instead; `HINBOX_PROFILE_UPDATE_APPROACH=rewrite` (or `update_profile(..., approach="rewrite")`) brings back the old whole-profile rewrite with reflection. `HINBOX_PROFILE_UPDATE_APPROACH=facts` uses the fact-list updater (`src/engine/fact_list.py`) instead; its rows (source kinds and quotes, repeat counts, which row a conflict disputes) are saved as a JSON string under `profile["fact_rows_json"]` and reloaded on the next update (`load_rows()`, which drops saved rows whose sentence is no longer in the text). Its extract step marks each claim `news` or background; news is handled first, at most one new background claim is kept per article, and at most two new claims from an article not mainly about the entity (`MAX_BACKGROUND_CLAIMS`, `MAX_PASSING_CLAIMS`; `fact_report["claim_log"]` has each claim's verdict and whether it was dropped). On dev it still states the article's main fact in only 21-25 of 38 labelled cases (edit-list Luna 33-34), because the model never extracts the rest. Its compare step has an `update` verdict for a later state of the same thing (moved camps, a decision after "still deciding"), written as a timeline entry next to the old one; a `conflict` must also pass `values_differ()` and `same_subject()` in code. A date check (`src/engine/date_disputes.py`, prompt `date_check.md`; off by default, `HINBOX_FACT_DATE_CHECK=on` turns it on) catches dates in background sentences the extract step skips: code pairs each dated article sentence with cited profile sentences that give a different year (or month) and share words (publication dates like "the May 2010 article" ignored), one model call judges each pair `conflict`/`different`/`later`, and a `conflict` is written right after the old sentence as "Another report differs: …"; a row already disputed is not disputed again. Pairs also need the words next to the two dates to overlap, and the model must name the one event both sentences date. On Luna it found two real profile errors (Khadr's plea year, Abbasi's release) but still wrote 1-3 wrong disputes per 160 cases, hence off by default.
10. **Profile Grounding**: Post-processing verification (`src/utils/grounding.py`) extracts citation markers from profile text (a grouped marker `^[a1, a2]` gives one claim per ID), looks up the cited source articles, and asks an LLM whether each article supports its claims. The pass (`src/engine/grounding_pass.py`) runs after all merging: `plan_grounding()` works out, per profile, which claims already have a verdict (kept from the stored report when the article text and claim text are the same and that article's last check succeeded; claim text never includes heading lines (`_extract_cited_claims()` drops them, so a paragraph over the claim cap shows the judge the same text under any heading) and is compared without extra spaces (`_claim_key()`), and the stored text must equal the part the judge would now see (the first `max_claim_chars` characters) or, when the claim is that long, start with it, so the old judge saw every word the new one would (`_earlier_verdict()`), so a sentence keeps its verdict when a sub-heading is put in front of it) and which are new (a claim of 40+ characters that is a whole sentence copied from the checked part of the article and names the entity, like a stub profile's quoted sentences, is "supported" with no call; a heading line stuck to the front of the claim, an opening quote mark and the article wrapping the sentence over two lines don't stop the match, so of a stub only an event's extracted description still goes to the model); `judge_pending()` then makes one call per article for the new claims of every profile that cites it (more than `HINBOX_GROUNDING_MAX_CLAIMS`, default 20, are split over calls; up to `grounding_workers` calls at once); `finish_report()` builds each `GroundingReport`. Each claim is sent numbered and with its entity's name, and the model is told to check every detail (names, relationships, numbers, directions, who said what; any wrong or added detail is "partial") and answers claim number, a short reasoning that names the passage it compared, then the verdict, without copying the claim back (`ClaimVerdict`, `HINBOX_GROUNDING_MAX_TOKENS` default 4096), so a reply can't run past the output limit by copying claims back. Each verdict also stores `passages`: the article words its reasoning quotes (and, with `HINBOX_GROUNDING_PASSAGE=on`, a passage the judge copies into its own field after the verdict; off by default: on the 64 hand labels on 10 Nov it changed 35% of Haiku's verdicts, matching 33 labels instead of 39, and made local Qwen's check 70% slower for 24 matched instead of 25, though doubted claims with a passage went from 17% to 91% (Haiku) and 20% to 64% (Qwen)), each looked up in the text the judge saw and stored as the article's own characters at that place, so a misquote or invented line is never stored (`src/utils/grounding_passages.py`: only case, spacing, curly quotes and dashes are forgiven; quotes under 20 characters or 4 words are dropped, and so is a quote the article has in more than one place, since the reader could not tell which one the judge read; the reader likewise marks only a passage found once in the text it shows). A verdict reused from an older report gains passages from its reasoning with no call; `just grounding-passages --entities <run> --articles <parquet> --out <copy>` (`scripts/grounding_passages.py`, `backfill_passages()` in `src/engine/grounding_pass.py`) does the same for a finished run without a model, writing a copy, verdicts and hashes untouched, and only for articles whose text still matches the stored hash. `verify_profile_grounding()` does the same for one profile. The report has a grounding score (supported + partial over all claims, so a near-1 score can hide wrong claims), claims per verdict (`supported`, `partial`, `not_supported`, `unclear`; `claim_counts()` recounts them from the verifications for older reports), per-claim support levels, and per-article `sources` (`SourceCheck`: checked/error/missing, with hashes of the article text and claims sent). A profile is skipped when `grounding_is_current()` says the stored report still holds (same text and citation count, no failed check, no missing article that is now available, no checked article whose text changed). Each profile's log line and the end-of-pass summary give those counts beside the score (`describe_claim_counts()`; the summary sums every stored report, `stored_claim_totals()`), as do speed-baseline summaries and the profile-create eval. `scripts/grounding_bench.py` re-runs the pass on a finished run's entities and compares verdicts claim by claim with the stored reports.
11. **Persistence**: Batched Parquet writes per entity type via `write_entities_table()` avoid write amplification. Every row is given every key before writing, because Arrow takes its columns from the first row only. Article processing status is tracked in a sidecar JSON file (`ProcessingStatus`) rather than rewriting the articles Parquet. Only the sidecar says an article is done: a `processing_metadata` column left in an articles file by the old in-Parquet status is ignored (`initialize_processing_metadata()`), since in the 12 Nov full run 13 articles whose column still said `processed: True` were skipped and never extracted. An article is marked processed only when every extraction and merge step worked: if an extraction call raised, a type's merge raised, a profile create/update call failed, or a match check or dispute call failed (`incomplete_reasons()` in `src/process_and_extract.py`; the merger counts these in `MergeStats.failed_profiles` and `MergeStats.failed_checks`), it is recorded as `incomplete` and retried next run. A failed match or dispute call (`check_failed()`, `dispute_failed()`) is not a "different" verdict: the incoming entity is neither merged nor created (before, it was created as a duplicate and the article marked done), the failure is not memoised or put in the review queue. Every SDK client's `create` is wrapped by `watch_connections()` (`src/utils/server_health.py`), which counts requests that could not connect, in a row across threads (timeouts and HTTP errors don't count; any answer resets it); after `HINBOX_MAX_CONNECTION_FAILURES` (default 20, `0` = never) the article loop raises `ModelServerUnreachable`, saves what is merged and exits 1, since on 9 Nov a local run lost its route to the model server after article 43 and spent 40 minutes failing every call. In the grounding pass the remaining checks then fail at once without a call (`judge_pending()`), are stored as `error` sources and asked again next run, and the run exits 1 after saving; the pass runs on every run unless `--skip-grounding`, even one with no new articles, so a resume redoes failed checks (current reports cost no call), and the log counts `profiles_with_failed_checks`. On macOS a local run's Python can get "No route to host" to a LAN model server for 10-40 minutes while curl still reaches it (Local Network privacy blocks non-Apple programs; four times on 9 Nov); allow the terminal or Python under Privacy & Security, Local Network, or reach the server through an SSH tunnel (`ssh -N -L 18080:127.0.0.1:8080 <server>`, then `OLLAMA_API_URL=http://127.0.0.1:18080/v1`). A failed profile update leaves the article unlinked from that entity so the retry updates the profile. Entity tables are written before the status sidecar (`save_entities_then_status()`), so a failed entity write leaves articles unprocessed. Both are saved every `HINBOX_SAVE_EVERY` merged articles (default 25, `0` = only at the end), and a SIGTERM (`kill`, shutdown) stops the run like Ctrl+C, so a crash in a 30-hour run loses at most the last 25 articles' merges, not everything since the start. Ctrl+C during article processing or the grounding pass saves the entities merged so far and exits with 130.

### Data Flow Architecture
- **Input**: Domain configs point to Parquet files with columns such as `id`, `title`, `content`, `url`, and `published_date`.
- **Processing**: `ArticleProcessor` orchestrates extraction for four entity types, records reflection metadata, runs QC checks (with retry), and keeps track of processing status. Each phase returns a `PhaseOutcome` carrying success/failure context. A single merge actor (the main thread) consumes extraction results in article order; within each article it merges the four entity types in parallel threads (`merge_parallel_types`), and each thread reads and writes only its own type's entity dict. The embedding-manager cache and the merge review queue file are locked.
- **Output**: Each run updates people/organizations/locations/events tables under the domain's output directory (`DomainConfig.get_output_dir()`).
- **Storage**: Entities include embeddings (with model/dimension/fingerprint metadata), provenance metadata, processing timestamps, profile version histories, and optional grounding reports.

### Model Architecture
- **Cloud Models**: Defaults come from `CLOUD_MODEL` in `src/constants.py` (default: `openai/gpt-6-luna`, the only cloud model scored on every eval) and are executed through provider-routed SDK clients (OpenAI SDK for OpenAI-compatible endpoints, Anthropic SDK for Claude models) with Instructor wrappers in `src/utils/llm.py`. Provider routing is handled by `src/utils/provider_routing.py`. A `List[Model]` request (extraction) is sent as one tool call holding `{"items": [...]}` and unwrapped, never one parallel tool call per item: in that mode GPT-6 Luna returned 1 event per article on 20 of 20 articles, and sometimes 1 person. Multi-tool-call recovery handles Instructor edge cases.
- **Extraction output limit**: extraction calls use `EXTRACTION_MAX_TOKENS` (env `HINBOX_EXTRACTION_MAX_TOKENS`, default 8192), because one reply holds every entity of a type and long articles' event lists ran past 2048 tokens, so the article was saved with no events.
- **Profile output limit**: profile create/update calls use `PROFILE_MAX_TOKENS` (env `HINBOX_PROFILE_MAX_TOKENS`, default 16384) instead of `DEFAULT_MAX_TOKENS` (2048), because each update rewrites the whole profile and 2048 tokens cut profiles off at about 6-7k characters.
- **Local Models**: Ollama is accessed via `OLLAMA_MODEL` (default: `ollama/qwen2.5:32b-instruct-q5_K_M`) for extraction, relevance checks, and match verification. Both models can be overridden via environment variables (`HINBOX_CLOUD_MODEL`, `HINBOX_OLLAMA_MODEL`), and each task can have its own (`HINBOX_<TASK>_MODEL`, see Configuration). Local calls use Instructor's `JSON_SCHEMA` mode, not tool calls, so the server constrains output to the schema; `List[Model]` responses are wrapped as `{"items": [...]}` and unwrapped before returning. Ollama calls send `reasoning_effort="none"` (thinking off) unless `HINBOX_OLLAMA_REASONING_EFFORT` says otherwise; when thinking may be on, their token limit is raised to at least `HINBOX_OLLAMA_THINKING_MAX_TOKENS` (default 8192). Before each Ollama call, `check_prompt_fits()` (`src/utils/ollama_context.py`) estimates the prompt at 4 characters per token and raises `PromptTooLongError` if it is longer than the model's `num_ctx` (read once from Ollama's `/api/show`, or `HINBOX_OLLAMA_NUM_CTX`), because Ollama silently cuts off the start of an over-long prompt, instructions included. With thinking on (`HINBOX_OLLAMA_REASONING_EFFORT` not `none`) the prompt must also leave `THINKING_RESERVE` (4096) tokens free, since the reasoning shares the window. `_sampling_kwargs()` in `src/utils/llm.py` adapts request parameters per model: OpenAI gpt-5/gpt-6/o-series get `max_completion_tokens` (plus `reasoning_effort="none"` where supported, so tool calling works), and Claude 5-family models get no `temperature`.
- **Embeddings**: `EmbeddingManager` (`src/utils/embeddings/manager.py`) chooses cloud/local/hybrid providers and caches vectors for similarity scoring. When `--local` is active, `ensure_local_embeddings_available()` enforces local-only mode.
- **Structured Output**: Dynamic Pydantic models in `src/dynamic_models.py` and list factories enforce schema consistency for both cloud and local responses.
- **Privacy Mode**: `--local` CLI flag calls `disable_llm_callbacks()` to disable all telemetry and forces local embedding mode.

### Frontend Architecture
The web reader (`src/frontend/`, `just frontend`) is a Starlette app that fills Jinja2 templates; it reads the entity Parquet tables and the domain's articles file and calls no model. See `src/frontend/CLAUDE.md`.
- **Pages** (`app.py`): home (search box, most-covered entities per table, "needs attention": pages with sentences the checker marked not supported), `/search`, one list per table (`/people` …, filters by name, type, kind of page, checker marks), entity pages (`/people/<key>`, `?version=N` for an older version), sources (`/sources`, `/sources/<id>`: stored text, entities named, profile sentences citing it), and `/panel`, the source panel fragment. Every page works without JavaScript; `static/reader.js` only opens a citation's source beside the profile (under the paragraph on narrow screens) and fades all but one kind of mark.
- **Profile rendering** (`profile_render.py`): walks the citation markers the same way `_extract_cited_claims()` in `src/utils/grounding.py` does, finds each claim's stored verdict in `profile_grounding.verifications`, wraps the claim in a span marked only when it is not fully supported (amber partly, red not supported, grey not checked), keeps each verdict's stored `passages` (the source panel marks them in the article, `_mark_passages()` in `views.py`, looked up again in the shown text so nothing unfound is marked), numbers citations by first appearance, shifts the top heading level to `h2` and builds the contents list. Profile text is HTML-escaped before Markdown.
- **Data** (`data_access.py`): `TABLES` lists the entity tables once (a new table is one `TableSpec`); `load_store()` keeps everything in memory until a Parquet file changes. `HINBOX_OUTPUT_DIR` and `HINBOX_ARTICLES_PATH` point it at another run. Kinds of page: `stub` (`profile["stub"]`), `link-only` (a hub type under `profiles.link_only` or `profile["linked_only"]`), `full`.
- **Views** (`views.py`): what each page shows; `CHECKER_MISSES` holds each grounding judge's hand-test miss count shown in the trust line (keep it in step with new measurements).
- **Corrections** (`src/utils/corrections.py`, `corrections_view.py`): a historian's corrections go into one append-only JSONL file outside every run folder (`corrections.path` in `config.yaml`, default `data/<domain>/corrections/corrections.jsonl`, `HINBOX_CORRECTIONS_PATH` overrides; article-derived, never commit it), never into the tables. Kinds: `strike` (optional `replacement` citing one source), `verdict` (overrules the checker for one sentence and source), `heading`, `rename`, `wrong_table`, `not_entity`, `split` (ticked sources are someone else), `join`; `withdraw` adds a line, nothing is deleted; a newer correction of the same sentence or page replaces the older one (kept, shown as replaced). Each names its page by key, name and linked article ids, and its sentence by `sentence_key()` (no markers, single spaces). `load_corrections()` lists unreadable lines under `problems` and splits undone by joins under `contradictions`. The reader's forms (`/correct/sentence` from the source panel, `/correct/page` under the name, `/corrections` list with Withdraw) append; pages draw strikes, the historian's sentences and verdicts on top (`Overlay` in `profile_render.py`); posts need the reader's own `Origin`/`Referer`; `HINBOX_REVIEWER` signs them. Each run carries out strikes in the stored profiles (`src/engine/corrections_pass.py`, design: https://claude.ai/artifact/Vu1gH2VgZge1QLoAeVAZhj): after merging and before grounding, `run_corrections_pass()` cuts each struck sentence still in its profile (and any claim saying it again with filler round it, `is_repeat()` both ways, so the true half of a struck sentence stays) and puts the historian's sentence with its citation in its place, puts back a historian's sentence that went missing (at the end of the profile), swaps a withdrawn strike's sentence back for the original (and an older strike's sentence, when a newer strike of the same sentence replaced it, before carrying the newer one out), and records the change as a profile version whose trigger is `corrections:<ids>` (`scripts/audit_entities.py` lists what those versions cut under `struck`, not `lost`). During updates, `guard_corrections()` (in `edit_profile()`, active inside `correction_scope()`, which `merge_entities()` opens around each update) cuts `add` sentences that restate a strike and drops a `replace` aimed at the historian's sentence. Each time it steps in, it logs a line and adds an entry (correction, page, what it did, the text) under `guarded` in the run report (`guard_log()`); each report row also carries `since`, the time of the run that last changed the tables for it, which `/corrections` shows ("by the run of 12 Nov 2026, 17:21 UTC"). A cut takes the sentence's own full stop with it when the model wrote it after the citation (`Leeds^[a1]. She`), and the historian's sentence gets one if theirs has none. Each correction gets a state (applied, held, re-applied with why, undone, waiting, needs a look with why) in `report-<time>.json`, `last-run.json` and the output folder's own `last-run-<hash>.json` (`latest_name()`; each run compares its tables with its own folder's last run, since runs into several folders share one corrections file) beside the corrections file, written only after the tables are saved, plus a log line (`describe_report()`); claims sharing a year and a name with a struck sentence are listed under `maybe_again`, unchanged. Verdicts are not written into grounding reports: the checker judges every run and the reader shows the historian's verdict over it; the report says held while the sentence's words stay. Pages are found by `resolve_ref()` (key, else name, else most shared sources), the same way in the reader and the pipeline; entity keys live in `src/utils/entity_keys.py` and claim spans in `src/utils/claim_spans.py`, both shared with the reader. The reader marks a historian's sentence a run put in the text as theirs and says on `/corrections` which run carried a strike out (`run_rows()`). Splits and joins are carried out at the start of each run, before merging (`carry_out_merges()` in `src/engine/corrections_merges.py`; its states go to the report through `run_corrections_pass(early=)`): a join feeds the page with fewer sources into the other, article by article, with `join_pair()` (`src/engine/kind_twins.py`, now any table) and keeps the smaller page's name as another name; a split moves the ticked sources to a new page (named by the form's optional `name`, else numbered, "Ann Lee (2)"; built as a run builds any page: a stub from the oldest ticked article, found by the name the articles use, then one update per further article), cuts each sentence citing only them (`drop_sources()`) and keeps a sentence citing both with only its other citations, listed under `split_mixed` in the report. During merging, `split_home()` sends a mention under a split's name from one of its sources to the one page holding sources of that side only, with no match check (on the full-run copy a ticked article seen again was turned away by the match check and made a third page), `join_target()` sends a mention spelled like the joined-in page (a name no page has any more) to the kept page with no match check, and `split_block()` passes over a candidate holding sources from the other side of a split (mention and page under the split's names only) before any model call; a same-named mention kept off its page is created under `split_create_key()`. A failed split step leaves the tables as they were and is reported as waiting; a join in which some article's update fails keeps the articles that did go in on the kept page, leaves both pages, is reported as waiting, and the next run asks only for the rest. Splits and joins in a contradiction are not carried out (needs a look); withdrawing one does not undo it. A correction made on a page that a join later removed is about the kept page (`joined_refs()` in `corrections_pass.py`, for the pass and for the edit guard while the articles are fed in). A join whose page an earlier join already removed joins the page it went into (`_find()`), and a sentence correction whose cited articles a split moved is about the page that holds them now (`resolve_correction()` in `src/utils/corrections.py`, which the reader uses too through `find_page()`), so the historian's sentence is not put back on the old page. After a split the kept page's `search_embedding` is cleared, since its evidence may be an article that left. Splits of one page, and of a page a split made, count as one family (`_family()`): a later split finds its sources on the page an earlier one made, and a mention goes to the page holding no source from the other side of any of them. A page a split or join placed a mention on keeps its key, and no merge re-keys a page onto a key another page holds. Headings, names and tables are reported as waiting.
- **Design**: Source Serif 4 for reading, IBM Plex Sans for the interface, teal-slate primary (`#2c5f7c`); tokens in `static/styles.css`, light and dark.

### File Structure Patterns
- **Engine Modules**: `article_processor.py`, `extractors.py`, `mergers.py` (with helpers `merge_candidates.py` for lexical blocking + similarity search and `merge_evidence.py` for evidence text + batch embedding), `match_checker.py`, `merge_dispute_agent.py`, and `profiles.py` are surfaced via `src/engine/__init__.py` for a stable import path.
- **LLM Helpers**: `src/utils/llm.py` and `src/utils/extraction.py` wrap SDK/Instructor interactions. `src/utils/provider_routing.py` resolves model prefixes to SDK targets. Multi-tool-call recovery in `llm.py` handles Instructor edge cases. Each SDK client is made once per target and reused for the whole run (`shared_client()` in `src/utils/client_cache.py`, also for cloud embeddings): a new client per call kept its sockets open until Python's cycle collector ran (tracing's `create` wrapper ties each client in a cycle), and after about 7,000 calls in the 8 Nov local run every new connection failed with "Connection error".
- **Embeddings**: Providers, manager, and similarity helpers live in `src/utils/embeddings/`.
- **Caching**: `src/utils/extraction_cache.py` provides the persistent sidecar cache; `src/utils/cache_utils.py` has a thread-safe LRU cache and stable hashing helpers shared across modules.
- **Name Handling**: `src/utils/name_variants.py` provides deterministic name normalisation, acronym detection/generation, equivalence expansion, and canonical name scoring — used by both QC and the merge pipeline.
- **Quality Controls**: `src/utils/quality_controls.py` (extraction QC, profile QC, `CITATION_RE`/`citation_ids()`), `src/utils/grounding.py` (profile grounding verification) and `src/utils/outcomes.py` (`PhaseOutcome` structured results) provide deterministic validation.
- **Processing Status**: `src/utils/processing_status.py` manages a sidecar JSON file tracking which articles have been processed, replacing the old in-Parquet status approach.
- **Tests**: `tests/` covers embedding accuracy, merger behaviour (lexical blocking, per-type thresholds, fingerprints), merge dispute agent routing, extraction caching and retry, canonical name selection, name variant detection, profile grounding, profile versioning, privacy mode enforcement, domain path resolution, and the web reader.
- **Speed baseline**: `just speed-baseline run --out <dir> --label <name> [--limit 20] [--set key=value]` picks a fixed article set once (`<dir>/articles.parquet`, same pick as `compare_extraction.py`) and runs the real pipeline (`--local --relevance-check`; `--cloud` drops `--local`) twice in fresh output folders (`HINBOX_OUTPUT_DIR`): `fresh` (nothing cached) and `cached` (the fresh pass's extraction cache and "not relevant" verdicts copied in; `--no-cached` skips it; `--seed-from <label>` runs only a cached pass from that run's fresh pass; `--no-grounding` passes the pipeline's `--skip-grounding`). It stops if the model server doesn't answer before a pass, and marks a run INVALID and exits 1 if over 5% of model calls fail (`--max-failed-share`). `--set` overrides a concurrency setting via `HINBOX_<KEY>` (e.g. `HINBOX_MAX_BUFFERED_ARTICLES`, `HINBOX_OLLAMA_IN_FLIGHT`). `<dir>/<label>/summary.json`/`.md` record commit, dirty files, models, `HINBOX_*`/`OLLAMA_*` settings (no keys), concurrency, what the model server reports (llama.cpp `/props`: context size, slots, build), timings and model-free quality counts (audit repeats/disputes/lost sentences/QC failures/name-variant duplicates, failed calls, incomplete articles, grounding scores); `compare --out <dir>` puts every run side by side. Outputs hold article text: keep them off GitHub.
- **Extraction comparison**: `scripts/compare_extraction.py run --models <m1> <m2> --out <dir>` runs the pipeline's extraction step (no merging) on the same Guantánamo articles per model and repeat; `compare --out <dir>` diffs the names each found (`diff.md`). Outputs hold article-derived text: keep them off GitHub (the repo is public).
- **Evaluation**: `src/evals/` holds the scoreboard: `datasets.py` loads gold sets into `EvalItem`s and assigns stable train/dev/test splits, `metrics.py` computes balanced accuracy and friends, `runner.py` runs a predictor (default: the pipeline's own relevance/match-check functions) and appends to `eval/scoreboard.jsonl`, `mine_merge_pairs.py` mines hard look-alike entity pairs for labelling, and `profile_replay.py` saves a profile snapshot after each create/update step for a set of well-covered entities, `profile_cases.py` builds `irrelevant`/`new_fact`/`disputed` test cases from those snapshots (disputed = next article with one cited year changed; replay entities have fixed splits in `ENTITY_SPLITS`), and `profile_update.py` scores updated profiles on those cases with deterministic checks. Hand checks of case labels go in `eval/profile_update_reviews.jsonl` (`{case_id, verdict: keep|drop, note, pairing?}`; `keep` makes a disputed case scored, `drop` removes a bad case; `pairing` = `case_pairing()`, which voids the verdict if a rebuild pairs different sentences), kept apart so `just eval-cases` can rebuild the cases. `claim_labels.py` reads `eval/claim_labels.jsonl` (one row per entity + article, `use: update|create`, `status: draft|reviewed`, `facts` with word-group `match` lists, `must_not` wrong readings); `load_cases()` attaches a label to its `new_fact` case and `score_claims()` can also score a newly created profile (`old_text=""`). `src/engine/profile_edits.py` is an alternative updater: the model returns `add`/`replace` edits anchored on existing sentences or headings (a heading anchor is found by its words at any level, and its section runs to the next heading of the same or a higher level, so it includes its sub-sections: `_section_end()`) (prompts: cloud models get `profile_edit.cloud.md`, which is `profile_edit.md` plus the local prompt's "is this really about the entity?" check and scored best for Luna and level with `.local` for Haiku over 245 train/dev/test cases; local `ollama/` models get `profile_edit.local.md`, a GEPA-tuned version that stops small models adding background from passing mentions but made cloud models skip real new facts; `profile_edit.md` is the plain fallback), and code applies them, so untouched text can't be dropped. `update_profile()` uses it by default. `create_profile()`/`update_profile()` take an optional `model` that overrides `HINBOX_CLOUD_MODEL`/`HINBOX_OLLAMA_MODEL` (an `ollama/` prefix means local).
- **Experiments**: `experiments/dspy_opt/` is a separate uv project (own `pyproject.toml`/`uv.lock`, Python 3.12) that depends on Hinbox by path. It holds DSPy versions of pipeline prompts (`merge.py`, `profile_update.py`) and a model factory (`lm.py`) that uses DSPy's native `lm15` engine. LiteLLM is excluded via an impossible `override-dependencies` marker, so never add it back. `src/` must not import from `experiments/`. Its tests live in `experiments/dspy_opt/tests/` and are not part of `just test`/CI.
- **Scripts**: Utility scripts in `scripts/` support domain management (`init_domain.py`, `list_domains.py`), data fetching, resets, and diagnostics. `scripts/audit_entities.py` spot-checks a finished run without a model: cited sentences lost between profile versions, repeated sentences, "sources disagree" sentences, citations that don't point at a linked article, name-variant duplicates, names in two tables, and misfiled types (`uv run python -m scripts.audit_entities <entities_dir> [--articles <parquet>] [--replay <eval>/profile_replay/<model>]`).

### Configuration
- **Models**: Configured in `src/constants.py` with cloud/local model specifications. Override defaults via `HINBOX_CLOUD_MODEL` and `HINBOX_OLLAMA_MODEL` env vars. `HINBOX_<TASK>_MODEL` (tasks: relevance, extraction, match, dispute, profile, grounding) gives one task its own model via `task_model()` in `src/utils/task_models.py`; the model's `ollama/` prefix decides local vs cloud, and `check_task_models()` stops a `--local` run at startup if any task is set to a cloud model. Each grounding report stores its judge under `model`; a report from another judge (or with none) is checked again in full on the next run, with no verdicts reused (`judged_by()` in `src/utils/grounding.py`). `scripts/grounding_bench.py run --model <m>` sets the judge for a bench run. Cloud runs judge grounding with `anthropic/claude-haiku-5-5` by default (`CLOUD_TASK_DEFAULTS`; needs `ANTHROPIC_API_KEY` and `uv sync --extra anthropic`), because on 64 hand-labelled claims it passed 2 of 42 wrong or partly wrong claims as supported (Luna 4, local Qwen 17); `--local` runs keep the local model. `HINBOX_GROUNDING_REASONING_EFFORT` (off by default) turns thinking on for a local grounding judge only, with `HINBOX_GROUNDING_THINKING_MAX_TOKENS` (default 16384) of room (`local_thinking()` in `src/utils/ollama_context.py`, a context variable read by `_sampling_kwargs()` and `check_prompt_fits()`); the effort is part of the judge name stored on reports. On the 64 labels Qwen3.6 with `high` matched ~35 instead of 25 and passed 11 of 42 bad claims instead of 19, but grounding took 67 min instead of 12 for 30 articles. Bolt without thinking scored 33 but doesn't fit on the GPUs beside the Qwen server; Bolt with thinking ran past 16k tokens on over half the articles. README "Choosing a grounding judge" has the table.
- **Prompt variants**: `DomainConfig.prompt_path(name, model)` picks `<name>.<family>.md` for a matching `prompt_families` entry in `config.yaml`, then `<name>.local.md` (`ollama/`) or `<name>.cloud.md`, then `<name>.md`; `HINBOX_PROMPT_VARIANT` forces one (`default` = plain file). Used for relevance, extraction and profile prompts (the merge check's prompt is in code). The eval scoreboard records which file each run used.
- **Dedup**: Per-entity-type similarity thresholds, lexical blocking, and merge gray-band/confidence settings configured in the `dedup` section of `configs/<domain>/config.yaml`
- **Extraction Cache**: Version-based invalidation via `cache.extraction.version` in domain config; cache files live under `{output_dir}/cache/extractions/v{version}/`
- **Step timings**: `src/utils/step_timing.py` times each pipeline step (`timed_step()` / `@timed`, nested per thread) and counts LLM calls under the active step via `cloud_llm_slot()`/`local_llm_slot()`, with slot-wait time kept apart from model time. Each run writes `{output_dir}/timings/run-<timestamp>.json` and prints a table; `timings/partial.json` is rewritten after every article.
- **Tracing**: `src/utils/tracing.py` records OpenTelemetry spans. `configure_tracing()` (called in `main()`) always writes every span to `{output_dir}/traces/run-<timestamp>.jsonl` and also sends them over OTLP/HTTP when `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (or `OTEL_EXPORTER_OTLP_ENDPOINT`) is set, e.g. Phoenix via `just phoenix`; a `--local` run refuses a non-local endpoint (`is_local_endpoint()`); `HINBOX_TRACING=off` disables it. Each article is its own trace (`start_article_span()`, entered in the extraction worker with `run_in_span()` and on the merge thread with `article_scope()`); `timed_step()` opens a span per step; `instrument_client()` replaces `create` on each SDK client in `_create_raw_client()` before Instructor wraps it, so every request (retries and fallbacks too) is a span with OpenInference attributes (messages, reply, tool-call arguments, `hinbox.llm.reasoning`, tokens, finish reason); `instrument_embeddings()` does the same for cloud embeddings; `log_decision()` adds each merge decision as a span event. For training data, each step calls `annotate()` with what its model call was about and how it ended (`hinbox.entity_name`, `hinbox.article_id`, `hinbox.is_match`, `hinbox.qc_flags`, `hinbox.edits_applied`…), `prompt_path()` notes the prompt file and its hash (`hinbox.prompt_files`, every file the step loaded), LLM spans carry `hinbox.step` and a system-prompt hash, the resource carries the git commit and `HINBOX_*` settings, and span limits are raised to 4096 so long conversations are not cut. `just eval` and `just eval-replay` are traced too, each eval item as its own trace with its gold label and result (`item_span()`). `scripts/export_training_data.py` (`just export-training`) turns traces into one `<task>.jsonl` per task of `{"messages", "tools", "metadata"}` rows (TRL/Unsloth/Axolotl format). Without `configure_tracing()` (tests) OpenTelemetry's tracer is a no-op.
- **Logging**: Structured Rich-based logging in `src/logging_config.py` with colour-coded decision lines (`DecisionKind`: NEW, MERGE, SKIP, DISPUTE, DEFER, ERROR) and gated profile panels (`--show-profiles`)
- **Privacy**: `--local` flag calls `disable_llm_callbacks()` and forces local embedding mode. The `_CALLBACKS_ENABLED` flag in `constants.py` controls telemetry.
- **Environment**: Requires `OPENAI_API_KEY` for the default cloud model and `ANTHROPIC_API_KEY` for the cloud grounding judge (`GEMINI_API_KEY` for Gemini), optional `OLLAMA_API_URL` for local

## Workflow Notes
- When finishing a chunk of work, check with the user to confirm the fix, then:
  1. Run `just format` to auto-fix formatting
  2. Run `just lint` to verify no remaining issues
  3. Run `just test` to execute the test suite
  4. Commit and push changes
- **Before pushing / opening a PR**, run `just ci` which executes the exact same
  checks as GitHub Actions:
  ```bash
  just ci
  ```
  All justfile recipes use `uv run` so there are no version mismatches between
  local and CI.

## Development Guidance
- The application has no users yet, so don't worry too much about backwards compatibility. Just make it work.
