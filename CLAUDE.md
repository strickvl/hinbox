# CLAUDE.md

This file provides guidance to Claude Code (claude.ai/code) when working with
code in this repository. Any design docs that you write can be stored in the
`design/` folder (which is ignored by git).

## Running commands

We use a `justfile` as the single task runner. Run `just` to see all available
commands, or `just <command>` to execute one. All recipes use `uv run` to
guarantee the lockfile venv is used (matching CI).

## Common Commands

### Development
- **Format code**: `just format` (ruff fix + format via `uv run`)
- **Lint code**: `just lint` (ruff check + format verification)
- **Run CI checks locally**: `just ci` (lint, file-length check, tests — the same recipes GitHub Actions calls)
- **File length limit**: `just check-file-length` fails if any tracked `.py` file is over 1000 lines. It runs in `just ci` and in GitHub Actions. Split the file rather than raising the limit.
- **Install dependencies**: `uv sync`

### Main Application
- **Process articles**: `just process` (CLI interface to main functionality)
- **Check database**: `just check` (view article statistics)
- **Start web interface**: `just frontend` (FastHTML web UI on localhost:5001)
- **Reset processing**: `just reset` (reset article processing status)
- **Domain management**: `just domains` / `just init <name>`
- **Evaluate a model**: `just eval <relevance|merge> --model <model>` scores it against the hand-labelled gold sets in `{output_dir}/eval/`; `just eval show` prints the scoreboard (`--grid`: latest score per model × prompt file); `--prompt-variant <name>` scores `<prompt>.<name>.md` whatever the model; `just eval-mine` picks hard merge pairs to label; `just eval-replay --model <model>` grows long profiles by replaying well-covered entities' articles in date order (snapshots for the profile-update eval); `just eval-cases --model <model>` turns those snapshots into profile-update test cases; `just eval profile-update --model <model> --split dev` runs the pipeline's profile update on those cases and scores it without a model (collapse, kept facts, unchanged text, added sentences, citing the article, invented citations, keeping both sides of a disputed year; a new-fact case with a claim label in `eval/claim_labels.jsonl` must also state each core fact in a sentence citing the article and add no listed wrong reading or invented "sources disagree" sentence, see `src/evals/claim_labels.py`; only `reviewed` labels count unless `--claim-labels draft`; `--rescore <run file>` scores a saved run again without model calls); it scores the edit-list updater (`src/engine/profile_edits.py`) that the pipeline uses; add `--approach rewrite` to score the old whole-profile rewrite instead, or `--approach facts` for the fact-list prototype (`src/engine/fact_list.py`: the model never sees the whole profile; it extracts quoted claims from the article, code finds the few existing sentences on the same thing, the model calls each claim same/new/conflict, a repeat is only counted on its row unless it comes from a new kind of source, a conflict is written by code right after the old sentence, and new facts are placed one section at a time; prompts `fact_extract.md`, `fact_compare.md`, `fact_write.md`)
- **DSPy experiments**: `just dspy-merge --model <model> --optimizer <none|bootstrap|mipro|gepa>` optimises the merge check and scores it on the same scoreboard; `just dspy-profile --model <model> --reflection-model <model>` runs GEPA on the edit-list profile updater and scores it with the profile-update eval; `just dspy-test` runs its offline tests

### Testing
- Run `just test` to execute the suite under `tests/`.
- Pass extra pytest args: `just test -k test_merger --tb=short`
- CI runs lint + tests on every PR via `.github/workflows/test.yml`.
- Key coverage areas include embedding similarity, lexical blocking, name-variant candidates, misfiled-location and misfiled-organization filtering, ALL CAPS recasing, spelling variants, per-type threshold resolution, embedding fingerprints, entity mergers, merge dispute agent routing, extraction caching/retry, canonical name selection, name variant detection, profile grounding, profile versioning, privacy mode enforcement, LLM multi-tool-call recovery, tracing (span nesting across threads, Instructor calls, `--local` endpoint guard), and frontend version navigation.
- Async tests (`@pytest.mark.asyncio`) are excluded in CI due to a missing pytest-asyncio configuration.

## Architecture Overview

### Entity Processing Pipeline
The CLI entry point `src/process_and_extract.py` coordinates the pipeline end to end using a parallel producer/consumer model:

1. **Configuration Loading**: `DomainConfig` reads `configs/<domain>/` to resolve Parquet input paths and output directories.
2. **Article Loading**: PyArrow loads the domain's article table and normalises rows before processing.
3. **Relevance Checking**: `ArticleProcessor.check_relevance` calls the helpers in `src/engine/relevance.py` (Gemini or Ollama) to skip irrelevant sources. Only runs with `--relevance-check`. It asks with the same labelled-section layout as the merge check (`src/utils/sectioned_prompt.py`): the domain's `relevance.md` minus its JSON "Output Format" section becomes the instructions, the article goes in its own section, and the model writes reasoning before `is_relevant`; an unreadable reply falls back to the structured prompt. If the check itself fails (API error, bad response), the article is skipped with reason `relevance_error`, kept separate from a real `not_relevant` verdict, and retried on the next run. A `not_relevant` verdict is stored in the processing-status sidecar with the article's content hash and a fingerprint of the model, prompt layout (`RELEVANCE_PROMPT_LAYOUT`) and relevance prompt (`ArticleProcessor.relevance_fingerprint()`); later runs reuse it without an LLM call while all three are unchanged (respects `cache.articles.skip_if_unchanged`; `--force-reprocess` re-checks).
4. **Parallel Extraction**: Multiple extraction workers process articles concurrently via `ThreadPoolExecutor`. Within each article, the 4 entity-type extractions also run in parallel. A shared LLM semaphore (`configure_llm_concurrency()`) bounds cloud API concurrency.
5. **Extraction Caching**: `ExtractionSidecarCache` (`src/utils/extraction_cache.py`) stores extraction outputs as JSON files keyed on content hash, model, entity type, prompt hash, schema hash, and temperature. Version-based invalidation lets you bump the cache version in config to force re-extraction without deleting files.
6. **Misfiled locations**: after the four extractions, `drop_misfiled_locations()` (`src/utils/misfiled_locations.py`) drops "locations" that are really people or organizations: a name that came back as a person in the same article (multi-word, or typed "other"), a name with an institution word ("Department", "Agency", "Sheriff"…), or an organization name from the same article or the organizations equivalence groups typed "other" (CIA, ACLU, ISIS, Senate). It also drops nationality words ("Yemeni"), news outlets ("Miami Herald"), laws ("NDAA") and dates ("March 2008"), whatever their type (`non_place_reason()` in `src/utils/non_place_names.py`). Dropped names go in `phase_outcomes["misfiled_locations"]`. The locations prompt also lists what isn't a location. `drop_misfiled_organizations()` drops an organization whose name is a person from the same article, titles and initials ignored ("President Donald Trump"), a country that came back as a `country` location from the same article ("France" typed "government" when an article lists countries), or a camp or base typed military/government/other ("Camp 7", "Guantanamo Bay Navy Base", "Guantánamo detention center"); dropped names go in `phase_outcomes["misfiled_organizations"]`. Before both, `recase_entity_names()` (`src/utils/name_case.py`) puts an ALL CAPS name copied from a dateline into the case the article uses elsewhere, or title-cases it for locations (`phase_outcomes["recased_names"]`).
7. **Quality Controls & Retry**: `src/utils/quality_controls.py` validates extraction output (required fields, name normalisation, within-article dedup) and profile quality (min length, citation regex, tag count, confidence range). Failures are captured in `PhaseOutcome` objects (`src/utils/outcomes.py`). When severe QC flags (`zero_entities`, `high_drop_rate`, `many_duplicates`, `many_low_quality_names`) are detected, the extractor automatically retries once with a repair hint. Profile QC runs inside `create_profile()` / `update_profile()` before each version is saved. First `repair_profile_citations()` (`src/utils/citation_ids.py`) snaps a cited article ID that isn't one of the profile's `sources` but is a few characters from exactly one of them back to that source (local Qwen sometimes drops or repeats a chunk of the ID), in the text and in saved fact rows, and adds the `citation_ids_repaired` flag. QC then applies safe fixes (default tags, clamped confidence) and records `{"passed", "flags"}` under `profile["qc"]`. A failing profile is kept and logged, never regenerated.
8. **Entity Merging**: `EntityMerger` follows an evidence-first cost structure — cheap checks run before expensive LLM calls:
   - **Lexical blocking**: RapidFuzz pre-filters candidates using configurable thresholds from the `dedup` section of domain config.
   - **Batched embeddings**: `embed_batch_result_sync()` computes vectors for all new entities at once rather than one-by-one.
   - **Similarity scoring**: Per-entity-type similarity thresholds and embedding fingerprints (`"{model}:{dim}"`) ensure model-change detection.
   - **Match checking**: LLM-based match verification only runs for candidates that pass the cheap filters. The prompt gives each input its own labelled `[[ ## field ## ]]` section (type rules included) and asks for written reasoning, then `is_match` and `confidence` under their own headers, as plain text via `text_generation()` (built with `src/utils/sectioned_prompt.py`; `parse_sectioned_reply()` reads it; an unparseable reply falls back to the structured `MatchCheckResult` prompt). On the hard merge eval set this layout plus reasoning cut false merges of related events; either one alone did not.
   - **Name-variant fallback**: when no candidate clears the similarity threshold, a candidate with a spelling variant of the incoming name still goes to the match check (`names_are_variants()` in `src/utils/name_variants.py`, searched over every entity, not just the capped lexical shortlist). Variants: the same name after `normalize_for_match()` (which drops accents, so "Guantánamo Bay" = "Guantanamo Bay"), a configured equivalence group ("Gitmo"), for locations/organizations the same core name without a leading "the"/"U.S.", a trailing "County"/"City" or a trailing "in/at/near …" description, one word respelled as a plural, ordinal or shortened form ("Commission"/"Commissions", "11"/"11th", "Counterterror"/"Counterterrorism"), or middle words dropped with the same first and last word ("Guantánamo Navy base" / "Guantánamo Bay Navy Base"); for organizations also "X administration"/"X government" with two spellings of one person ("Bush administration" / "George W. Bush administration"); for people the same first and last name ("Donald J. Trump"), the same last name with a first name shortened or one letter off ("Clay"/"Clayton", "Shelley"/"Shelly"), or the reverse, a bare surname ("Trump"), or a two-word-or-longer end of the full name ("Hadi al Iraqi" / "Abd al Hadi al Iraqi"); for events the same words in any order ("Firing of Harvey Rishikof as convening authority") or one run of up to two words added ("CIA waterboarding of …" / "Waterboarding of …"; words added in two places don't count). Common transliterations count as one spelling for people and events (Sheik/Shaikh/Sheikh, Mohammed/Muhammad, Qaida/Qaeda). A lone first or middle name ("Lara" / "Lara Tur", `lone_name_in_full_name()`) goes to the match check only when exactly one person in the table fits, so a bare "John" with ten Johns goes nowhere. Substring containment and derived acronyms don't count. On the merge gold set this sends 22 of 25 labelled-same pairs to the match check (was 12) and 1 of 166 labelled-different pairs (unchanged). If the match check rejects the closest candidate, the best name-variant candidate gets one more match check.
   - **Merge dispute agent**: When a match result falls in the "gray band" (similarity within ±`MERGE_GRAY_BAND_DELTA` of threshold) with confidence below `MERGE_UNCERTAIN_CONFIDENCE_CUTOFF`, `MergeDisputeAgent` provides a second-stage LLM analysis that can override the initial merge/skip decision. Deferred cases are appended to `{output_dir}/merge_review_queue.jsonl` for human review. When the final verdict is skip or defer, the incoming entity is created as a new entity rather than dropped (unless an entity with the same key already exists, which is never overwritten).
   - **Canonical name selection**: 5-layer deterministic scoring (`score_canonical_name()` in `src/utils/name_variants.py`) picks the best display name, penalizing acronyms, generic phrases, contextual suffixes, and ALL CAPS names (`is_shouting_name()`; a same-name-in-normal-case incoming entity replaces an ALL CAPS one).
9. **Profile Versioning**: `src/engine/profiles.py` maintains `VersionedProfile` history whenever entity content changes. Creation generates a first draft, then runs up to 3 reflect/regenerate rounds (`iterative_improve()`). Updates apply a list of edits from one model call (`src/engine/profile_edits.py`, no reflection); `HINBOX_PROFILE_UPDATE_APPROACH=rewrite` (or `update_profile(..., approach="rewrite")`) brings back the old whole-profile rewrite with reflection. `HINBOX_PROFILE_UPDATE_APPROACH=facts` uses the fact-list updater (`src/engine/fact_list.py`) instead; its rows (source kinds and quotes, repeat counts, which row a conflict disputes) are saved as a JSON string under `profile["fact_rows_json"]` and reloaded on the next update (`load_rows()`, which drops saved rows whose sentence is no longer in the text). Its compare step has an `update` verdict for a later state of the same thing (moved camps, a decision after "still deciding"), written as a timeline entry next to the old one; a `conflict` must also pass `values_differ()` and `same_subject()` in code.
10. **Profile Grounding**: Post-processing verification (`verify_profile_grounding()` in `src/utils/grounding.py`) extracts citation markers from profile text (a grouped marker `^[a1, a2]` gives one claim per ID), looks up the cited source articles, and uses an LLM to check each article's claims (one call per article). The `GroundingReport` includes a grounding score, per-claim support levels, and per-article `sources` (`SourceCheck`: checked/error/missing, with hashes of the article text and claims sent). The pass (`src/engine/grounding_pass.py`) checks up to `grounding_workers` profiles at once after all merging. It skips a profile only when `grounding_is_current()` says the stored report still holds (same text and citation count, no failed check, no missing article that is now available, no checked article whose text changed); otherwise the stored report is passed in and only articles that failed, became available, or whose claims changed go back to the model.
11. **Persistence**: Batched Parquet writes per entity type via `write_entities_table()` avoid write amplification. Every row is given every key before writing, because Arrow takes its columns from the first row only. Article processing status is tracked in a sidecar JSON file (`ProcessingStatus`) rather than rewriting the articles Parquet. An article is marked processed only when every extraction and merge step worked: if an extraction call raised, a type's merge raised, or a profile create/update call failed (`incomplete_reasons()` in `src/process_and_extract.py`; the merger counts these in `MergeStats.failed_profiles`), it is recorded as `incomplete` and retried next run. A failed profile update leaves the article unlinked from that entity so the retry updates the profile. Entity tables are written before the status sidecar (`save_entities_then_status()`), so a failed entity write leaves articles unprocessed. Ctrl+C during article processing or the grounding pass saves the entities merged so far and exits with 130.

### Data Flow Architecture
- **Input**: Domain configs point to Parquet files with columns such as `id`, `title`, `content`, `url`, and `published_date`.
- **Processing**: `ArticleProcessor` orchestrates extraction for four entity types, records reflection metadata, runs QC checks (with retry), and keeps track of processing status. Each phase returns a `PhaseOutcome` carrying success/failure context. A single merge actor (the main thread) consumes extraction results in article order; within each article it merges the four entity types in parallel threads (`merge_parallel_types`), and each thread reads and writes only its own type's entity dict. The embedding-manager cache and the merge review queue file are locked.
- **Output**: Each run updates people/organizations/locations/events tables under the domain's output directory (`DomainConfig.get_output_dir()`).
- **Storage**: Entities include embeddings (with model/dimension/fingerprint metadata), provenance metadata, processing timestamps, profile version histories, and optional grounding reports.

### Model Architecture
- **Cloud Models**: Defaults come from `CLOUD_MODEL` in `src/constants.py` (default: `openai/gpt-6-luna`, the only cloud model scored on every eval) and are executed through provider-routed SDK clients (OpenAI SDK for OpenAI-compatible endpoints, Anthropic SDK for Claude models) with Instructor wrappers in `src/utils/llm.py`. Provider routing is handled by `src/utils/provider_routing.py`. A `List[Model]` request (extraction) is sent as one tool call holding `{"items": [...]}` and unwrapped, never one parallel tool call per item: in that mode GPT-6 Luna returned 1 event per article on 20 of 20 articles, and sometimes 1 person. Multi-tool-call recovery handles Instructor edge cases.
- **Extraction output limit**: extraction calls use `EXTRACTION_MAX_TOKENS` (env `HINBOX_EXTRACTION_MAX_TOKENS`, default 8192), because one reply holds every entity of a type and long articles' event lists ran past 2048 tokens, so the article was saved with no events.
- **Profile output limit**: profile create/update calls use `PROFILE_MAX_TOKENS` (env `HINBOX_PROFILE_MAX_TOKENS`, default 16384) instead of `DEFAULT_MAX_TOKENS` (2048), because each update rewrites the whole profile and 2048 tokens cut profiles off at about 6-7k characters.
- **Local Models**: Ollama is accessed via `OLLAMA_MODEL` (default: `ollama/qwen2.5:32b-instruct-q5_K_M`) for extraction, relevance checks, and match verification. Both models can be overridden via environment variables (`HINBOX_CLOUD_MODEL`, `HINBOX_OLLAMA_MODEL`), and each task can have its own (`HINBOX_<TASK>_MODEL`, see Configuration). Local calls use Instructor's `JSON_SCHEMA` mode, not tool calls, so the server constrains output to the schema; `List[Model]` responses are wrapped as `{"items": [...]}` and unwrapped before returning. Ollama calls send `reasoning_effort="none"` (thinking off) unless `HINBOX_OLLAMA_REASONING_EFFORT` says otherwise; when thinking may be on, their token limit is raised to at least `HINBOX_OLLAMA_THINKING_MAX_TOKENS` (default 8192). Before each Ollama call, `check_prompt_fits()` (`src/utils/ollama_context.py`) estimates the prompt at 4 characters per token and raises `PromptTooLongError` if it is longer than the model's `num_ctx` (read once from Ollama's `/api/show`, or `HINBOX_OLLAMA_NUM_CTX`), because Ollama silently cuts off the start of an over-long prompt, instructions included. With thinking on (`HINBOX_OLLAMA_REASONING_EFFORT` not `none`) the prompt must also leave `THINKING_RESERVE` (4096) tokens free, since the reasoning shares the window. `_sampling_kwargs()` in `src/utils/llm.py` adapts request parameters per model: OpenAI gpt-5/gpt-6/o-series get `max_completion_tokens` (plus `reasoning_effort="none"` where supported, so tool calling works), and Claude 5-family models get no `temperature`.
- **Embeddings**: `EmbeddingManager` (`src/utils/embeddings/manager.py`) chooses cloud/local/hybrid providers and caches vectors for similarity scoring. When `--local` is active, `ensure_local_embeddings_available()` enforces local-only mode.
- **Structured Output**: Dynamic Pydantic models in `src/dynamic_models.py` and list factories enforce schema consistency for both cloud and local responses.
- **Privacy Mode**: `--local` CLI flag calls `disable_llm_callbacks()` to disable all telemetry and forces local embedding mode.

### Frontend Architecture

- **Routes**: Modular route handlers in `routes/` (home, people, organizations, locations, events)
- **Data Access**: Centralized data loading from Parquet files (`data_access.py`)
- **Filtering**: Search and filter utilities (`filters.py`)
- **Components & Helpers**: Shared UI building blocks (`components.py`) — confidence badges, version selectors, tag pills, alias display — and helpers for profile versions (`entity_helpers.py`)
- **Configuration**: App setup, shared state, and `main_layout()` sidebar+content layout (`app_config.py`)
- **Design System**: Crimson Pro headings, IBM Plex Sans body, warm teal-slate primary (`#2c5f7c`), amber accent (`#c97b3a`) — CSS variables in `static/styles.css`
- **Static Assets**: CSS and font loading under `static/`

### File Structure Patterns
- **Engine Modules**: `article_processor.py`, `extractors.py`, `mergers.py` (with helpers `merge_candidates.py` for lexical blocking + similarity search and `merge_evidence.py` for evidence text + batch embedding), `match_checker.py`, `merge_dispute_agent.py`, and `profiles.py` are surfaced via `src/engine/__init__.py` for a stable import path.
- **LLM Helpers**: `src/utils/llm.py` and `src/utils/extraction.py` wrap SDK/Instructor interactions. `src/utils/provider_routing.py` resolves model prefixes to SDK targets. Multi-tool-call recovery in `llm.py` handles Instructor edge cases.
- **Embeddings**: Providers, manager, and similarity helpers live in `src/utils/embeddings/`.
- **Caching**: `src/utils/extraction_cache.py` provides the persistent sidecar cache; `src/utils/cache_utils.py` has a thread-safe LRU cache and stable hashing helpers shared across modules.
- **Name Handling**: `src/utils/name_variants.py` provides deterministic name normalisation, acronym detection/generation, equivalence expansion, and canonical name scoring — used by both QC and the merge pipeline.
- **Quality Controls**: `src/utils/quality_controls.py` (extraction QC, profile QC, `CITATION_RE`/`citation_ids()`), `src/utils/grounding.py` (profile grounding verification) and `src/utils/outcomes.py` (`PhaseOutcome` structured results) provide deterministic validation.
- **Processing Status**: `src/utils/processing_status.py` manages a sidecar JSON file tracking which articles have been processed, replacing the old in-Parquet status approach.
- **Tests**: `tests/` covers embedding accuracy, merger behaviour (lexical blocking, per-type thresholds, fingerprints), merge dispute agent routing, extraction caching and retry, canonical name selection, name variant detection, profile grounding, profile versioning, privacy mode enforcement, domain path resolution, and frontend history rendering.
- **Extraction comparison**: `scripts/compare_extraction.py run --models <m1> <m2> --out <dir>` runs the pipeline's extraction step (no merging) on the same Guantánamo articles per model and repeat; `compare --out <dir>` diffs the names each found (`diff.md`). Outputs hold article-derived text: keep them off GitHub (the repo is public).
- **Evaluation**: `src/evals/` holds the scoreboard: `datasets.py` loads gold sets into `EvalItem`s and assigns stable train/dev/test splits, `metrics.py` computes balanced accuracy and friends, `runner.py` runs a predictor (default: the pipeline's own relevance/match-check functions) and appends to `eval/scoreboard.jsonl`, `mine_merge_pairs.py` mines hard look-alike entity pairs for labelling, and `profile_replay.py` saves a profile snapshot after each create/update step for a set of well-covered entities, `profile_cases.py` builds `irrelevant`/`new_fact`/`disputed` test cases from those snapshots (disputed = next article with one cited year changed; replay entities have fixed splits in `ENTITY_SPLITS`), and `profile_update.py` scores updated profiles on those cases with deterministic checks. Hand checks of case labels go in `eval/profile_update_reviews.jsonl` (`{case_id, verdict: keep|drop, note, pairing?}`; `keep` makes a disputed case scored, `drop` removes a bad case; `pairing` = `case_pairing()`, which voids the verdict if a rebuild pairs different sentences), kept apart so `just eval-cases` can rebuild the cases. `claim_labels.py` reads `eval/claim_labels.jsonl` (one row per entity + article, `use: update|create`, `status: draft|reviewed`, `facts` with word-group `match` lists, `must_not` wrong readings); `load_cases()` attaches a label to its `new_fact` case and `score_claims()` can also score a newly created profile (`old_text=""`). `src/engine/profile_edits.py` is an alternative updater: the model returns `add`/`replace` edits anchored on existing sentences or headings (prompts: cloud models get `profile_edit.cloud.md`, which is `profile_edit.md` plus the local prompt's "is this really about the entity?" check and scored best for Luna and level with `.local` for Haiku over 245 train/dev/test cases; local `ollama/` models get `profile_edit.local.md`, a GEPA-tuned version that stops small models adding background from passing mentions but made cloud models skip real new facts; `profile_edit.md` is the plain fallback), and code applies them, so untouched text can't be dropped. `update_profile()` uses it by default. `create_profile()`/`update_profile()` take an optional `model` that overrides `HINBOX_CLOUD_MODEL`/`HINBOX_OLLAMA_MODEL` (an `ollama/` prefix means local).
- **Experiments**: `experiments/dspy_opt/` is a separate uv project (own `pyproject.toml`/`uv.lock`, Python 3.12) that depends on Hinbox by path. It holds DSPy versions of pipeline prompts (`merge.py`, `profile_update.py`) and a model factory (`lm.py`) that uses DSPy's native `lm15` engine. LiteLLM is excluded via an impossible `override-dependencies` marker, so never add it back. `src/` must not import from `experiments/`. Its tests live in `experiments/dspy_opt/tests/` and are not part of `just test`/CI.
- **Scripts**: Utility scripts in `scripts/` support domain management (`init_domain.py`, `list_domains.py`), data fetching, resets, and diagnostics. `scripts/audit_entities.py` spot-checks a finished run without a model: cited sentences lost between profile versions, repeated sentences, "sources disagree" sentences, citations that don't point at a linked article, name-variant duplicates, names in two tables, and misfiled types (`uv run python -m scripts.audit_entities <entities_dir> [--articles <parquet>] [--replay <eval>/profile_replay/<model>]`).

### Configuration
- **Models**: Configured in `src/constants.py` with cloud/local model specifications. Override defaults via `HINBOX_CLOUD_MODEL` and `HINBOX_OLLAMA_MODEL` env vars. `HINBOX_<TASK>_MODEL` (tasks: relevance, extraction, match, dispute, profile) gives one task its own model via `task_model()` in `src/utils/task_models.py`; the model's `ollama/` prefix decides local vs cloud, and `check_task_models()` stops a `--local` run at startup if any task is set to a cloud model.
- **Prompt variants**: `DomainConfig.prompt_path(name, model)` picks `<name>.<family>.md` for a matching `prompt_families` entry in `config.yaml`, then `<name>.local.md` (`ollama/`) or `<name>.cloud.md`, then `<name>.md`; `HINBOX_PROMPT_VARIANT` forces one (`default` = plain file). Used for relevance, extraction and profile prompts (the merge check's prompt is in code). The eval scoreboard records which file each run used.
- **Dedup**: Per-entity-type similarity thresholds, lexical blocking, and merge gray-band/confidence settings configured in the `dedup` section of `configs/<domain>/config.yaml`
- **Extraction Cache**: Version-based invalidation via `cache.extraction.version` in domain config; cache files live under `{output_dir}/cache/extractions/v{version}/`
- **Step timings**: `src/utils/step_timing.py` times each pipeline step (`timed_step()` / `@timed`, nested per thread) and counts LLM calls under the active step via `cloud_llm_slot()`/`local_llm_slot()`, with slot-wait time kept apart from model time. Each run writes `{output_dir}/timings/run-<timestamp>.json` and prints a table; `timings/partial.json` is rewritten after every article.
- **Tracing**: `src/utils/tracing.py` records OpenTelemetry spans. `configure_tracing()` (called in `main()`) always writes every span to `{output_dir}/traces/run-<timestamp>.jsonl` and also sends them over OTLP/HTTP when `OTEL_EXPORTER_OTLP_TRACES_ENDPOINT` (or `OTEL_EXPORTER_OTLP_ENDPOINT`) is set, e.g. Phoenix via `just phoenix`; a `--local` run refuses a non-local endpoint (`is_local_endpoint()`); `HINBOX_TRACING=off` disables it. Each article is its own trace (`start_article_span()`, entered in the extraction worker with `run_in_span()` and on the merge thread with `article_scope()`); `timed_step()` opens a span per step; `instrument_client()` replaces `create` on each SDK client in `_create_raw_client()` before Instructor wraps it, so every request (retries and fallbacks too) is a span with OpenInference attributes (messages, reply, tool-call arguments, `hinbox.llm.reasoning`, tokens, finish reason); `instrument_embeddings()` does the same for cloud embeddings; `log_decision()` adds each merge decision as a span event. For training data, each step calls `annotate()` with what its model call was about and how it ended (`hinbox.entity_name`, `hinbox.article_id`, `hinbox.is_match`, `hinbox.qc_flags`, `hinbox.edits_applied`…), `prompt_path()` notes the prompt file and its hash (`hinbox.prompt_files`, every file the step loaded), LLM spans carry `hinbox.step` and a system-prompt hash, the resource carries the git commit and `HINBOX_*` settings, and span limits are raised to 4096 so long conversations are not cut. `just eval` and `just eval-replay` are traced too, each eval item as its own trace with its gold label and result (`item_span()`). `scripts/export_training_data.py` (`just export-training`) turns traces into one `<task>.jsonl` per task of `{"messages", "tools", "metadata"}` rows (TRL/Unsloth/Axolotl format). Without `configure_tracing()` (tests) OpenTelemetry's tracer is a no-op.
- **Logging**: Structured Rich-based logging in `src/logging_config.py` with colour-coded decision lines (`DecisionKind`: NEW, MERGE, SKIP, DISPUTE, DEFER, ERROR) and gated profile panels (`--show-profiles`)
- **Privacy**: `--local` flag calls `disable_llm_callbacks()` and forces local embedding mode. The `_CALLBACKS_ENABLED` flag in `constants.py` controls telemetry.
- **Environment**: Requires `OPENAI_API_KEY` for the default cloud model (`GEMINI_API_KEY`/`ANTHROPIC_API_KEY` for those providers), optional `OLLAMA_API_URL` for local

## Workflow Notes
- When finishing a chunk of work, check with the user to confirm the fix, then:
  1. Run `just format` to auto-fix formatting
  2. Run `just lint` to verify no remaining issues
  3. Run `just test` to execute the test suite
  4. Commit and push changes
- **Before pushing / opening a PR**, run `just ci` which executes the exact same
  checks as GitHub Actions:
  ```bash
  just ci
  ```
  All justfile recipes use `uv run` so there are no version mismatches between
  local and CI.

## Development Guidance
- The application has no users yet, so don't worry too much about backwards compatibility. Just make it work.
